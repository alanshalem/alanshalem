# Blog

> This repo is also the GitHub profile of [@alanshalem](https://github.com/alanshalem): the [root `README.md`](../README.md)
> is the profile page (its images are generated by `tooling/profile/`) and this one, in `docs/`, is the project's.
> GitHub shows the first README it finds in `.github/`, the root and `docs/`, on the profile and on the repo page,
> so the project README must not live in `.github/` or the root.

A self-hosted blog with a Markdown editor, built for a small VPS shared with other apps.

## How it is built

```
Visitor ──► Caddy ──► static files (HTML precompressed with br/gzip)
                 │
                 ├─ /media/*   uploaded images and videos (immutable cache, Range)
                 ├─ /admin/*   admin SPA (React, precompressed; hashed assets immutable)
                 └─ /api/*     .NET API  (/api/internal is blocked from outside; /api/admin/* not cached)

Admin ──► API ──► SQLite
              └─ on publish ──► Builder ──► astro build ──► releases/<timestamp>/ ──► `current` symlink (atomic swap)
```

On the VPS, Dokploy's Traefik sits in front of Caddy and terminates TLS (see "Operations").

The home hero rotates on every visit between photos and short videos (≤ 15 s) uploaded from Settings. Every image is
stored optimized (AVIF + WebP at several widths, no metadata, with libvips) and every video is trimmed, stripped of its
audio and encoded with ffmpeg to AV1 + H.264 at 720p and 1080p.

The idea: **visitors never touch the API or the database**. Everything public is pre-generated HTML, so the server
barely works at rest and the site stays up even if the API goes down.

| Folder | What it is |
|---|---|

## Local development

Requirements: Node ≥ 22.18, pnpm 10, .NET SDK 11 and, for hero videos, `ffmpeg` and `ffprobe` with `libsvtav1`
(SVT-AV1 4.x, the version the encoding was calibrated with) and `libx264`. The API looks for them on the PATH;
otherwise set `Video:FfmpegPath` and `Video:FfprobePath`. Videos being processed live in `Video:WorkDirectory`
(default `data/video-work`, never inside `Media:Directory`). libvips is not needed: it ships in the NuGet package.

```bash
pnpm install            # and commit pnpm-lock.yaml: the images install with --frozen-lockfile
pnpm test               # every Node test (see "How to verify")
pnpm typecheck

# API (port 5090)
cd apps/api && dotnet test && dotnet run --project src/Blog.Api

# Admin (proxies /api and /media to :5090)
pnpm dev:admin          # http://localhost:5173/admin/

# Public site
pnpm build:web
```

## Development with Docker

No .NET, Node or ffmpeg to install: only Docker. From the repo root:

```bash
docker compose -f infra/compose.dev.yml --env-file infra/local.env up --build   # Ctrl+C to stop; `down` removes the containers
```

`--env-file infra/local.env` brings the admin password and the test token: the same file the local production copy
uses, so they change in one place. It goes on every command of this compose project (`up`, `logs`, `down`), as in the
local copy; without it, compose names the missing variable and does nothing.

| What | URL | Live reload |
|---|---|---|
| Admin (Vite) | http://localhost:5173/admin/ — password `admin` | HMR on save |
| Site (`astro dev`) | http://localhost:4321/ | reloads the page |
| API (`dotnet watch`, Development) | http://localhost:5090/api/health | hot reload / restart |

- The code is mounted from your disk. `node_modules`, `bin/obj`, the NuGet packages and the data (SQLite, media,
  videos being processed) live in volumes of the `blog-dev` project: they do not mix with the Windows ones nor with
  the `dotnet run` database. `docker compose -f infra/compose.dev.yml --env-file infra/local.env down -v` deletes them
  (database included).
- The first start downloads dependencies (~1 min); later ones take ~20 s. If `pnpm-lock.yaml` changes, the `deps`
  service reinstalls on its own the next time the stack comes up.
- Ports in use (for example because you also run the servers without Docker): change your machine's ports with
  `API_PORT`, `ADMIN_PORT` and `WEB_PORT`, for example
  `API_PORT=15090 ADMIN_PORT=15173 WEB_PORT=14321 docker compose -f infra/compose.dev.yml --env-file infra/local.env up`.
  The admin's "View site" links follow `WEB_PORT`. The admin reaches the API over the compose network (`API_URL`).
- Another password: generate a hash (see below) and paste it into `infra/local.env` (it applies to development and to
  the local copy). The token between the API and the site (`BUILDER_TOKEN`) is a test value; any value works as long
  as it has 32 characters or more.
- Without Docker, `pnpm dev:admin` uses `http://localhost:5090` (API) and `http://localhost:4321/` (site); `API_URL` and
  `SITE_URL` change them.

## Local production copy

The VPS's own `docker-compose.yml` (same images, memory caps and volumes: Caddy + API + builder, static site,
`/admin/`, `/media`) with an override for your machine: plain HTTP without TLS on http://localhost:8080 and test values
in `infra/local.env` (only for your machine; never on the VPS). From `infra/`:

```bash
docker compose -f docker-compose.yml -f compose.local.yml --env-file local.env up -d --build
docker compose -f docker-compose.yml -f compose.local.yml --env-file local.env logs -f builder   # first site build
docker compose -f docker-compose.yml -f compose.local.yml --env-file local.env down             # -v also deletes the data
```

http://localhost:8080/ → `/es/`; the admin is at http://localhost:8080/admin/ with the password `admin`. If 8080 is
taken: `LOCAL_PORT=18080 docker compose ...` (it also adjusts `SITE_URL`). Right after `up`, `/api` answers 502 for
the second or two the API takes to start; Caddy checks it every 2 s.

To change the password, generate the hash with the API image (already built by `up --build`) and paste it into
`local.env` in single quotes:

```bash
docker compose -f docker-compose.yml -f compose.local.yml --env-file local.env run --rm --no-deps api hash-password
```

## How to verify

The same as CI (`.github/workflows/ci.yml`, on every push and PR to `master`), from the repo root:

```bash
# Node (typecheck, tests of every workspace + profile + skills + infra, admin build, skills in sync)
pnpm install --frozen-lockfile
pnpm typecheck && pnpm test && pnpm --filter @blog/admin build && pnpm agents:check

# API: in the dev target of its Dockerfile (SDK + the pinned ffmpeg 9.1), so the ffmpeg tests run too. The code is
# mounted read-only and copied inside without bin/, obj/ or the development database: nothing on your machine changes.
docker build --target dev --tag blog-api-dev apps/api
docker run --rm --volume "$PWD/apps/api:/src:ro" blog-api-dev sh -euc \
  'mkdir /tmp/api && tar -C /src --exclude=bin --exclude=obj --exclude=./src/Blog.Api/data -cf - . | tar -C /tmp/api -xf - &&
   cd /tmp/api && dotnet build -warnaserror && dotnet test --no-build'

# Infra: the compose files (the VPS one needs its .env; CI tests it with fake values) and the Caddyfile with the image's Caddy
docker compose -f infra/docker-compose.yml -f infra/compose.local.yml --env-file infra/local.env config -q
docker compose -f infra/compose.dev.yml --env-file infra/local.env config -q
docker run --rm -v "$PWD/infra/caddy/Caddyfile:/etc/caddy/Caddyfile:ro" -e SITE_ADDRESS=:80 \
  "$(sed -n 's/^FROM \(caddy:[^ ]*\).*/\1/p' infra/caddy/Dockerfile)" caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
# The Caddyfile running (production, staging behind a proxy, a stub API): noindex, robots.txt, the 404 in the URL's or
# the browser's language, the proxy gate, the proxy secret kept from the API and the access log
sh infra/test/caddy-runtime.sh

# Security: dependencies with known vulnerabilities
pnpm audit --prod --audit-level high
```

CI also builds the three production images (`docker compose build`, no push) and scans them with Trivy (CRITICAL and
HIGH with a published fix), looks for secrets in the whole history with gitleaks and runs `dotnet list package
--vulnerable --include-transitive` with the pinned SDK. Dependabot (`.github/dependabot.yml`) proposes new versions of
pnpm, NuGet, base images and actions every week. Every action is pinned by SHA and every image by digest.

On Windows the backup script tests are skipped (they are for Linux) and, without Developer Mode, so are the builder
tests that create symlinks; in CI (Linux) they all run.

## Operations (VPS)

Production (`alanshalem.com`) and staging (`staging.alanshalem.com`) run on **Dokploy** (srv2192513): its Traefik owns
ports 80/443 and the Let's Encrypt certificates, and this stack's Caddy listens on :80 inside `dokploy-network`
(`infra/compose.dokploy.yml`). Visitors get the same responses as with Caddy at the edge. The same
`docker-compose.yml` also runs on a plain VPS with only Docker, where Caddy does TLS itself ("First deploy (VPS without
Dokploy)" below).

Every command runs from `infra/` with `--env-file .env` (without it, compose names the missing variable and does
nothing). Under Dokploy, `infra/` is `/etc/dokploy/compose/<appName>/code/infra` (as root): the `.env` Dokploy writes
there names the project (`COMPOSE_PROJECT_NAME=<appName>`) and both compose files (`COMPOSE_FILE`), so the commands and
scripts below find that environment's stack as they are.

How Dokploy runs a Compose service: on every deploy it clones the branch into `/etc/dokploy/compose/<appName>/code`,
rewrites the Compose Path file (`infra/docker-compose.yml`) adding the Traefik labels of its domains and
`dokploy-network`, writes `infra/.env` from the Environment tab and runs the Command (Advanced) from `code/` with
`docker` in front. The compose file on the VPS is therefore not the one in git (never edit it there: the next deploy
replaces it), and the containers are `<appName>-<service>-1` (for example `<appName>-caddy-1`), the names the checks
below use.

Set up the two Traefik middlewares below before the first deploy: the domain of each environment points at them.

### Dokploy: proxy secret

`dokploy-network` is shared by every Dokploy app on the VPS, so any container on it can call this Caddy directly
(`<appName>-caddy-1:80`), skipping Traefik. To tell Traefik's requests apart, Traefik adds a secret header to every
request it forwards and Caddy answers 403 to any request without it (`PROXY_SECRET`, Caddyfile "Proxy gate"): a
container that calls Caddy directly cannot skip the staging basic auth, and cannot forge `X-Forwarded-For` (Caddy only
believes it from private addresses, and the login rate limit is per IP). The secret never goes to git: it lives in the
service's Environment tab and in Traefik's dynamic configuration, on the VPS only. Caddy keeps it from the API and its
logs.

1. On your machine, one per environment: `openssl rand -hex 32`. Each one goes to its environment's Environment tab
   as `PROXY_SECRET=...` ("Dokploy: first deploy", step 5).
2. Dokploy → Traefik File System → `dynamic/` (on the VPS: `/etc/dokploy/traefik/dynamic/`), new file
   `alanshalem-proxy-secret.yml` (Traefik reloads it on its own), with each environment's value:

   ```yaml
   http:
     middlewares:
       alanshalem-production-proxy-secret:
         headers:
           customRequestHeaders:
             X-Proxy-Secret: "<production PROXY_SECRET>"
       alanshalem-staging-proxy-secret:
         headers:
           customRequestHeaders:
             X-Proxy-Secret: "<staging PROXY_SECRET>"
   ```

The domain gets it in "Dokploy: first deploy" (step 6) and the check is its step 8. To rotate it: change the value in
Traefik's file and in the Environment tab, then Deploy (between the two steps the site answers 403).

### Dokploy: staging basic auth and noindex

Staging asks for a user and password in Traefik (before anything reaches this stack) and, with `SITE_ENV=staging`,
Caddy adds `X-Robots-Tag: noindex, nofollow` to every response and serves a `robots.txt` that disallows everything.
The password never goes to git: only its bcrypt hash, and only on the VPS.

1. On your machine, the hash (the password is typed twice, without echo):
   `docker run --rm -it httpd:2.4-alpine htpasswd -nB staging` → `staging:$2y$05$...`.
2. Dokploy → Traefik File System → `dynamic/` (on the VPS: `/etc/dokploy/traefik/dynamic/`), new file
   `alanshalem-staging-auth.yml` (Traefik reloads it on its own; `$` stays as is in this file):

   ```yaml
   http:
     middlewares:
       alanshalem-staging-auth:
         basicAuth:
           removeHeader: true   # the API never sees the Authorization header
           users:
             - "staging:$2y$05$..."
   ```

The staging domain gets it in "Dokploy: first deploy" (step 6), next to its proxy secret; the check is step 8.

Why in Traefik and not in Caddy: Dokploy attaches middlewares to a Compose domain, and Traefik checks the password
before the request reaches the blog. Dokploy's Security tab (basic auth form) exists only for Applications. Nobody
skips it by calling Caddy directly: without the proxy secret Caddy answers 403.

### Dokploy: first deploy (once per environment)

Each environment is its own Dokploy Compose service: its own project name (`<appName>`), volumes, database, media,
session keys and builder token. Nothing is shared between staging and production. Before it: the Traefik files of
"Dokploy: proxy secret" and, for staging, "Dokploy: staging basic auth and noindex".

1. DNS: `A` records for `alanshalem.com` and `staging.alanshalem.com` pointing to the VPS IP.
2. Dokploy → Settings → Git → GitHub: connect the GitHub account (GitHub App) with access to this repository.
3. Projects → Create Project `alanshalem`, with two environments, `production` and `staging`. In each one: Create
   Service → Compose, type **Docker Compose** (not Stack: Stack cannot `build`), provider GitHub, this repository,
   branch `master`, Compose Path `./infra/docker-compose.yml`. Leave Isolated Deployments off. Save.
4. Advanced → Command, with the App Name shown in the General tab. Dokploy runs this exact command from `code/` with
   `docker` in front; it adds `compose.dokploy.yml`, which takes Caddy off 80/443 and puts it behind Traefik, and
   `--wait` makes the deploy wait until every container is running and healthy (step 7):

   ```text
   compose -p <appName> --env-file infra/.env -f infra/docker-compose.yml -f infra/compose.dokploy.yml up -d --build --remove-orphans --wait
   ```

5. Environment (Dokploy writes it to `infra/.env` on every deploy; edit it here, never on the server). Staging:

   ```bash
   SITE_ADDRESS=:80
   SITE_URL=https://staging.alanshalem.com
   SITE_ENV=staging
   BUILDER_TOKEN=...
   ADMIN_PASSWORD_HASH='pbkdf2-sha256$...'
   PROXY_SECRET=...
   COMPOSE_FILE=docker-compose.yml:compose.dokploy.yml
   ```

   - Production: `SITE_URL=https://alanshalem.com` and no `SITE_ENV` line (the default is `production`). `SITE_ENV`
     only accepts `production` or `staging`: any other value stops Caddy (it refuses its configuration), so a typo
     never serves staging as an indexable production, and the deploy fails (step 7).
   - `BUILDER_TOKEN`: `openssl rand -hex 32`, a different one per environment.
   - `PROXY_SECRET`: this environment's value in Traefik's file ("Dokploy: proxy secret"). Without it the deploy fails
     (compose names the variable).
   - `ADMIN_PASSWORD_HASH`: in single quotes (it contains `$`), generated on your machine with
     `docker build --tag blog-api apps/api && docker run --rm -it blog-api hash-password` (12 characters or more,
     typed without echo).
   - `COMPOSE_FILE` is for the commands and scripts run on the VPS (`backup.sh`, `restore.sh`, `docker compose ...`);
     Dokploy's own deploy passes the files in its command. `ACME_EMAIL` is not used: Traefik requests the
     certificates.
6. Domains → Add Domain: Service Name `caddy`, Host `staging.alanshalem.com` (or `alanshalem.com`), Path `/`,
   Container Port `80`, HTTPS on, Certificate Provider Let's Encrypt, and Middlewares: production
   `alanshalem-production-proxy-secret@file`; staging `alanshalem-staging-proxy-secret@file` and
   `alanshalem-staging-auth@file`. Save (a Compose service applies domain changes on the next deploy).
7. Deploy and follow the deployment log: `init-permissions` runs once and exits with 0 (a one-shot, which `--wait`
   accepts), then `api`, `caddy` and `builder` report `Healthy` and the deploy is done; the builder then builds the
   site (Logs tab of `builder`). **A failed deploy** is marked as an error in the Deployments tab and its log ends with
   `container <appName>-<service>-1 is unhealthy` (or `exited`): that service's Logs tab says why (a `SITE_ENV` typo:
   `File to import not found: site-env-prod`). Nothing is rolled back: what the deploy recreated stays (a Caddy that
   refuses its configuration leaves the domain answering 404 from Traefik) until a deploy with the fix.
8. Check it, from your machine (and the second check on the VPS):
   - `curl -I https://alanshalem.com/` answers 302 to `/es/` or `/en/`. Staging: without credentials 401;
     `curl -I -u staging https://staging.alanshalem.com/` answers 302 with `X-Robots-Tag: noindex, nofollow`. If the
     site answers 403, the proxy secret middleware is missing from the domain or its value differs from `PROXY_SECRET`.
   - Nobody skips Traefik: `docker run --rm --network dokploy-network curlimages/curl -s -o /dev/null -w
     '%{http_code}\n' http://<appName>-caddy-1/` prints `403`.
   - The API sees the visitor's real IP (the login rate limit and the logs depend on it): a wrong login,
     `curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'X-Requested-With: blog-admin' -H 'Content-Type:
     application/json' -d '{"password":"wrong"}' https://alanshalem.com/api/auth/login` (staging: add `-u staging`)
     prints `401`, and then `docker logs --since 5m <appName>-api-1 2>&1 | grep 'Failed login'` shows
     `Failed login from <your public IP>`. A private address (`10.…`, `172.…`) means every visitor shares one login
     rate limit: check `CADDY_TRUSTED_PROXIES` (`compose.dokploy.yml`) and the address Traefik itself sees.
   - Open `https://<domain>/admin/`, sign in, create a post and publish it.
9. Automatic deploys, in General: staging with Auto Deploy on and the trigger on push (branch `master`); production
   with Auto Deploy on and the trigger on tag (see "Dokploy: release flow").

**Verify on the first real deploy.** These Dokploy behaviours were checked locally (Traefik v3.7 and the compose file
rewritten as Dokploy does), not on a real Dokploy: confirm them once per environment and fix this runbook if one
differs.

- [ ] Compose domains have the Middlewares field and it reaches Caddy's router: `docker inspect --format
      '{{json .Config.Labels}}' <appName>-caddy-1` lists the middlewares of step 6. Without them Caddy answers 403 to
      everything (it fails closed: nothing is exposed).
- [ ] The tag trigger: `git push origin <tag>` starts a production deploy and no staging one; a push to `master` only
      staging.
- [ ] `COMPOSE_PROJECT_NAME=<appName>` is in the env file Dokploy writes (`backup.sh` and `restore.sh` need it):
      `grep -c '^COMPOSE_PROJECT_NAME=' /etc/dokploy/compose/<appName>/code/infra/.env` prints `1`. If it prints `0`,
      add that line to the Environment tab.
- [ ] The `$` of the single-quoted `ADMIN_PASSWORD_HASH` survives the Environment tab: signing in to `/admin/` with
      the password works (a mangled hash rejects every password).
- [ ] `--wait` works in Dokploy's deploy: the deployment log ends with the `Healthy` lines of step 7.

### Dokploy: release flow

- Push to `master` → staging deploys on its own. It does not wait for CI: check the run is green before trusting
  staging. Commits whose message carries `[skip ci]` (the daily profile images) deploy nothing.
- When staging is right: `git tag vYYYY.MM.DD && git push origin vYYYY.MM.DD` → production deploys. **Dokploy deploys
  the head of the configured branch, not the tagged commit** (it clones `--branch master --depth 1`): tag the head of
  `master` that staging validated and do not push anything else before the production deploy starts.
- Before tagging, a backup of production (`sh backup.sh` in its `infra/`): it is the only way back (see Rollback).
- Each deploy rebuilds the images and recreates only the containers whose image or configuration changed; the volumes
  stay. Migrations run when the API starts and a failed build never touches the published site.
- A deploy that does not change Caddy keeps the site up. One that does (the Caddyfile, the admin, its image or
  environment, such as `SITE_ENV` or `PROXY_SECRET`) leaves the domain without Caddy for about 5 s: Traefik answers 404
  from when the old one stops until the new one is healthy (it only routes to healthy containers; measured behind
  Traefik v3.7, ~3 s of that is the old Caddy stopping).
- Dokploy's Deployments tab keeps the logs of each deploy; its Logs tab, the containers' logs.

### First deploy (VPS without Dokploy)

1. Docker with the compose plugin, and the domain's DNS pointing to the VPS IP.
2. `cp .env.example .env` and fill it in (`.env` is not versioned; never commit it):
   - `SITE_ADDRESS` (the domain, e.g. `blog.example.com`) and `SITE_URL` (`https://` + domain, no trailing slash).
   - `BUILDER_TOKEN`: `openssl rand -hex 32` (the API requires 32 characters or more).
   - `ADMIN_PASSWORD_HASH`: the hash of the admin password, in single quotes (it contains `$`). The password must have
     12 characters or more; it is typed without echo:

     ```bash
     docker build --tag blog-api ../apps/api && docker run --rm -it blog-api hash-password
     ```

   - `ACME_EMAIL` (optional): email for Let's Encrypt notices (expirations, certificate problems).
3. `docker compose --env-file .env up -d --build` and `docker compose --env-file .env ps` until `api` and `builder`
   show `healthy`. Caddy requests the TLS certificate on its own at startup (with the DNS already pointing).
4. Open `https://your-domain/admin/`, create a post and publish it. The first build takes a while; later ones are
   debounced and run with `nice` and a heap cap so they do not get in the way of the other apps.

If the VPS already has another reverse proxy on 80/443, do not bring this Caddy up as is: put yours in front and point
it at the `caddy` container over an internal network, as `compose.dokploy.yml` does for Traefik (no published ports,
`SITE_ADDRESS=:80`, `CADDY_TRUSTED_PROXIES`, and `PROXY_SECRET` sent by your proxy as `X-Proxy-Secret`). The API
publishes no ports: only Caddy and the builder reach it.

### Update

Under Dokploy an update is a push (staging) or a tag (production): see "Dokploy: release flow". Without Dokploy:

```bash
sh backup.sh                                   # always first: it is the only way back (see Rollback)
git pull
docker compose --env-file .env up -d --build
docker compose --env-file .env ps              # api and builder are healthy again
docker image prune -f                          # the old images left without a name
```

Database migrations run on their own when the API starts. A failed build never touches the published site.

**Deploying the version that adds the session epoch logs the admin out once.** Session cookies issued before that
version carry no epoch, so the new API rejects them: sign in again after the update. Later updates keep the session.

### Rollback

There are no `Down` migrations: going back to a previous version means **restoring the backup** taken before
updating. First the previous code (`git checkout <commit>` and `docker compose --env-file .env build`; under Dokploy, a
revert on `master` and a new tag, deployed), then the backup from that moment:

```bash
sh restore.sh /var/backups/blog/daily/<UTC>            # checks the snapshot and shows what it would do; changes nothing
sh restore.sh /var/backups/blog/daily/<UTC> --apply    # restores, brings everything up, waits for the healthchecks and requests a build
```

Whatever was published or edited after that backup is lost, except in `BACKUP_DIR/pre-restore-<UTC>`: before
changing anything, `--apply` saves what was there (it is restored with the same script; it is not rotated, delete it
when you no longer want it). **Every restore logs the admin out** (new session keys): a backup predates some logout,
and if it brought its keys back, a cookie that logout revoked would be valid again.

### Backups

`backup.sh` copies the database (a consistent copy made by the API while it keeps serving) and the new media to
`BACKUP_DIR` (default `/var/backups/blog`), and rotates 7 daily and 4 weekly snapshots. Once a day with cron, as the
user that runs Docker:

```cron
15 3 * * * BACKUP_RCLONE_REMOTE=secret:blog sh /path/to/the/repo/infra/backup.sh >> /var/log/blog-backup.log 2>&1
```

Under Dokploy, in root's crontab, one line per environment with its own `BACKUP_DIR` (two environments in one folder
would rotate each other's snapshots). The script reads the `.env` Dokploy wrote next to it, so it finds that
environment's stack; it exists after the first deploy, and a deploy re-clones the folder, so keep backups away from
deploy times:

```cron
15 3 * * * BACKUP_DIR=/var/backups/alanshalem BACKUP_RCLONE_REMOTE=secret:alanshalem sh /etc/dokploy/compose/<appName>/code/infra/backup.sh >> /var/log/alanshalem-backup.log 2>&1
```

`restore.sh` the same way (`BACKUP_DIR=... sh /etc/dokploy/compose/<appName>/code/infra/restore.sh <snapshot>`).
Dokploy's Volume Backups do not replace this: they copy the volume as it is, and a SQLite database being written can
be copied half-way; `backup.sh` asks the API for a consistent copy and leaves the session keys out on purpose.

- Without `BACKUP_RCLONE_REMOTE`, the backup stays only on the VPS: if the disk is lost, everything is lost. Set up a
  remote copy with rclone: a **`crypt`** remote (`rclone config` → crypt) on top of whatever S3, B2, Drive… you use.
  The backup holds the database (with the admin hash and the drafts): the script rejects an unencrypted remote unless
  `BACKUP_ALLOW_PLAINTEXT=1`. It uploads with `rclone copy` (a deletion here never deletes there); the full
  configuration is at the top of `backup.sh` and `backup-common.sh`.
- Test the restore now and then: `sh restore.sh <snapshot>` (without `--apply`) checks that the snapshot is sound.
- On a new VPS: the repo, the previous `.env` (keep it somewhere else: it is not in the backup),
  `rclone copy "$BACKUP_RCLONE_REMOTE" /var/backups/blog`, `docker compose --env-file .env build` and `restore.sh` as
  above. Under Dokploy: create the service and deploy it once ("Dokploy: first deploy", with the previous values), copy
  the backup with rclone and run its `restore.sh`.

### Logs

```bash
docker compose --env-file .env logs -f --tail 100 api        # or caddy, builder
docker compose --env-file .env logs --no-log-prefix api | jq -R 'fromjson? // empty'   # the API writes JSON
```

They are capped: `local` driver, at most 5 files of 10 MB per container (they never fill the disk). Failed logins are
in the API log with the IP. The admin does not show the state of builds: a failed build is in `logs builder` (and the
published site is still the previous one).

### Healthchecks

- `api`: `dotnet Blog.Api.dll healthcheck` asks `/api/health/ready` (200 if SQLite answers, otherwise 503).
  `/api/health` only says the process is alive; it is the one Caddy uses to take the API out of rotation.
- `builder`: `node src/healthcheck.ts` asks its `GET /health`. It starts once the API is healthy (`service_healthy`).
- `caddy`: `wget` asks its own admin endpoint (`127.0.0.1:2019`, inside the container only, never published): healthy
  once its configuration loaded, so `up --wait` (the Dokploy deploy, `restore.sh`) fails when Caddy refuses it. It
  does not ask the API, and Caddy starts as soon as the API has started (`service_started`), without waiting for it to
  be healthy: the static site never depends on the API.

`docker compose --env-file .env ps` shows the state; an `unhealthy` service keeps running (Docker does not restart
it): check its logs. Behind Dokploy, Traefik only routes to a healthy Caddy.

### Rotate the admin password and the builder token

- Password: generate the new hash (as in the first deploy), replace `ADMIN_PASSWORD_HASH` in `.env` and run
  `docker compose --env-file .env up -d api` (under Dokploy: in the service's Environment tab, then Deploy). Then sign
  in to the admin with the new password and log out: logging out invalidates every open session (a copied cookie
  too).
- Token: `openssl rand -hex 32`, replace `BUILDER_TOKEN` in `.env` and run `docker compose --env-file .env up -d` (the
  API and the builder read it at startup; under Dokploy: Environment tab, then Deploy).

### Firewall

Open only SSH, 80/tcp and 443 (tcp and udp, HTTP/3). For example with ufw: `ufw allow OpenSSH`, `ufw allow 80/tcp`,
`ufw allow 443`, `ufw enable` (or the VPS provider's firewall). Careful: Docker opens the ports it publishes in
iptables without going through ufw; here only Caddy publishes them (80 and 443). Under Dokploy only its Traefik
publishes 80/443; this stack publishes nothing.

### Disk

- `docker system df` shows images, build cache and volumes. After several updates: `docker system prune` (stopped
  containers, unnamed images, build cache). **Never** `--volumes` nor `down -v`: they delete the database and the media.
- The media (`media`) grows with every uploaded image and video (several AVIF and WebP widths are kept for each image)
  and is never deleted on its own; the backup accumulates it too. The builder keeps the last 3 versions of the site
  (`KEEP_RELEASES`).

### Monitoring

There is no internal monitoring. Set up an external availability check (any uptime service) with email alerts on:

- `https://your-domain/` (the static site: what visitors see),
- `https://your-domain/api/health/ready` (the API and the database: the admin),
- the TLS certificate expiration (Caddy renews it on its own; under Dokploy, Traefik; the alert tells you if renewal
  fails).

Staging is behind basic auth: a check there needs the credentials (or watch production only).

## Security (what is implemented)

- Session cookie `__Host-admin`: HttpOnly, SameSite=Strict, Secure, 12 h. Logging out invalidates every issued session
  (session epoch in the database).
- Password with PBKDF2-SHA256 (600k iterations), 12 characters or more; only the hash goes in `.env`.
- CSRF: mandatory `X-Requested-With: blog-admin` header on the admin routes.
- Login rate limit: 10 attempts / 15 min per IP (the real IP: `X-Forwarded-For` is only believed when it comes from the
  Docker networks, `ForwardedHeaders:KnownNetworks`). Caddy sends the API one address, the visitor's; behind Dokploy it
  is the one Traefik reports (Caddy trusts it with `CADDY_TRUSTED_PROXIES`; Traefik drops what a visitor sends), and
  only on requests that carry Traefik's `X-Proxy-Secret` (`PROXY_SECRET`): any other request gets a 403, so another
  container on the shared `dokploy-network` can neither forge it nor skip the staging basic auth.
- Image uploads validated by *magic bytes* (PNG, JPG, GIF, WebP, AVIF), max 8 MB; SVG rejected on purpose.
- Videos (MP4, MOV, WebM, MKV) validated by *magic bytes* and ffprobe, max 200 MB and 15 s; the original (with audio
  and metadata) never reaches `/media`.
- Markdown **does not accept raw HTML** (everything is escaped) and URLs pass an allowlist (`http`, `https`, `mailto`,
  `tel`, relative).
- `/api/internal` (used by the builder) requires a Bearer token and Caddy blocks it from outside.
- Containers with `no-new-privileges`, no Linux capabilities except the ones needed, `pids_limit` and memory caps;
  Caddy and the API with a read-only filesystem; the API and the builder do not run as root (Caddy does, but only with
  the capability to open ports 80/443). Base images pinned by digest.
- A failed build **never touches** the published site.
